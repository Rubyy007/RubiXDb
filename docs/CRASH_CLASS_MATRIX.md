## 0. Read this first

* **Kill-9 is not power-loss evidence.** Every class B row is a *process* death: the operating system and its page cache survive, so every byte a returned `write()` handed over is visible to the next process whether or not it was ever synced. A missing `fsync` is therefore **invisible** to every row in section 2. No class B result appears, or may be copied, in a class C (power-loss) column.
* **Class A** (section 1): an `error=` action makes the call site's `Result` an `Err` while the process lives; the engine's real failure path runs. Supports error-path claims only.
* **Class C** (simulated power loss) and **class D** (storage error preventing recovery): sections 3 and 4 are **empty**: the D1c matrix has not been run (D1b built the simulator and a *smoke* cycle - `docs/PERSISTENCE_MODEL.md` §7 - which is not this matrix). There is no power-loss capability on this platform (Windows `fsync_dir` is a no-op; no `dm-flakey`, no hardware cut rig). **Power loss: NOT TESTED.**
* Expected state for every class A/B row (docs/DURABILITY_CONTRACT.md §8): recovery succeeds (or refuses fail-closed, class D), and the recovered keyspace equals `model(K)` per writer for some `K` with `acked <= K <= submitted` (R1–R4, R12); the first post-recovery write is numbered above every acknowledged seq and the checkpoint (R6); a second recovery changes nothing (R10); the stopped, recovered directory passes the physical checker (R7/R8) and has no leftover `*.sst.tmp` (R11). R5 is **not** independently observable at key-value level (only the engine's own `RecoveryStats` identity is checked). The oracle is independent of the engine under test: expected data is regenerated from the seed and from the child's ledger of submitted/acknowledged operations; it compares every key and value, never counts.
* A row is PASS only if the execution log names the requested point, the process was stopped there (abort status, or parked and killed by the parent), **and** the oracle accepted the recovered state. `POINT NOT REACHED` and `KILL TIMEOUT` are FAIL.

## 5. Where the evidence is thin (kept visible)

* Torn-tail fixtures (`recover/TornWalTail`, `recover/TornManifestTail`) and the stale-file fixtures are **synthetic** bytes appended by the test, not states observed after a crash.
* A kill between two `write_all` calls leaves a prefix; it does not model a single write torn inside a sector (class C).
* Windows `fsync_dir` is a no-op, so the `*.dir_sync` points kill before/after a call that does nothing on this platform; the state they leave is still the ordering state, but no durability claim follows.
* The concurrent column is non-deterministic and currently exposes F-D1a-1 (above).
